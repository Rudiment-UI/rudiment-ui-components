# Accessibility

## Built on React Aria

Nearly every interactive component in Rudiment UI is built on Adobe's [React Aria](https://react-spectrum.adobe.com/react-aria/) library. React Aria is one of the most well-tested accessibility foundations available for React, handling the complex parts of accessible UI so you don't have to. A few simpler components, such as Breadcrumb, are made from native HTML elements like `<nav>` and `<a>`, which are accessible by default. Buttons inside other components, such as Pagination's page buttons and the dismiss buttons on Tag and Alert, use React Aria's `useButton`, so they handle mouse, touch and keyboard the same way.

### What React Aria provides automatically

- **Accessible Rich Internet Applications (ARIA) attributes:** correct roles, states, and properties applied to every component
- **Keyboard navigation:** full keyboard support following WAI-ARIA design patterns
- **Focus management:** focus moves to the right place at the right time (for example, into a dialog when it opens)
- **Screen reader support:** announcements, labels, and descriptions that work across screen readers

## Keyboard support by component

Every component can be operated without a mouse. Here's what keyboard users can expect:

| Component               | Keyboard behavior                                                          |
| ----------------------- | -------------------------------------------------------------------------- |
| **Button / IconButton** | `Space` or `Enter` to activate                                             |
| **Input**               | Standard text input behavior                                               |
| **Checkbox / Switch**   | `Space` to toggle                                                          |
| **RadioGroup**          | Arrow keys to move between options, `Space` to select                      |
| **Select**              | Arrow keys to navigate options, `Enter` to select, `Escape` to close       |
| **Dialog**              | `Tab` cycles focus within the dialog (focus is trapped), `Escape` to close |
| **Tooltip**             | Appears on focus, `Escape` to dismiss                                      |
| **Tag**                 | With `onPress` and `dismissible`, the tag and its remove button are two separate buttons. `Tab` moves between them, and `Space` or `Enter` activates either. |
| **Rating** (with `onChange`) | One tab stop for the whole group. Arrow keys move and select, and `Home`/`End` jump to the first or last star |
| **NavItem**             | `Space` or `Enter` to activate (link or button), `Tab` to move between items |
| **Breadcrumb**          | `Tab` to move between links, `Enter` to activate (the current page is plain text, marked `aria-current="page"`) |
| **Pagination**          | `Tab` to move between page controls, `Space` or `Enter` to activate (the active page is marked `aria-current="page"`) |
| **KanbanBoard**         | `Space` or `Enter` on a card's handle picks it up. Arrow keys move it within and across columns, `Space` drops it and `Escape` cancels. Each step is announced. |
| **ProgressBar / CircularProgress** | Not interactive. They report progress to assistive technology with `aria-valuenow` |

## Focus indicators

All interactive elements display a visible focus ring when navigated to via keyboard. These focus indicators meet Web Content Accessibility Guidelines (WCAG) 2.1 AA requirements, so keyboard users always know where they are on the page.

### Theme-specific focus styles

The default theme uses a standard CSS `outline` for focus rings. Several industry themes replace this with a layered `box-shadow` ring that gives interactive elements a more sculpted look. Both approaches meet the same WCAG contrast requirements. If you create a custom theme, you can follow either pattern in your component CSS.

## Color contrast

Token values meet WCAG 2.1 AA contrast requirements:

- **Text on backgrounds:** 4.5:1 minimum contrast ratio
- **UI elements** (borders, icons, controls): 3:1 minimum contrast ratio

This applies to all built-in themes, in both light and dark variants.

## Live regions

These components announce changes that appear dynamically, so screen reader users don't miss them:

- **Alert** uses `role="alert"` for urgent messages (the default) and `role="status"` for polite, non-urgent updates (the `isPolite` prop).
- **Toast**: `RudiToastRegion` is a landmark (`F6` moves focus into it), and each toast is announced when it appears.
- **KanbanBoard** announces drag progress with card labels and column titles, for example "Design homepage is over In Progress, position 2 of 3."

## Meaning beyond color

No status is shown by color alone:

- **StatCard:** pairs the trend color with an icon and screen reader text, such as "Increased +12.5%". Use `trendLabel` to change the wording.
- **Badge with `dot`:** still announces its children ("3 unread") as visually hidden text. A dot with no children is decorative.
- **Avatar:** `statusLabel` adds the status to the accessible name ("Ada Lovelace, Busy"). An avatar with neither `alt` nor `name` is decorative.
- **Image:** if the image fails to load, the fallback keeps the `alt` text as its accessible name.

## Localizable labels

Built-in control labels can be overridden for translation. Examples are `closeLabel` on `RudiDialog` and `RudiToastRegion`, and `trendLabel` on `RudiStatCard`. Components that render their own navigation landmark, such as Breadcrumb and Pagination, take a `label` prop.

## Progress reporting

**ProgressBar** and **CircularProgress** use `role="progressbar"` with `aria-valuenow`, `aria-valuemin`, and `aria-valuemax` attributes (provided by React Aria's `useProgressBar` hook). Screen readers announce the current progress value along with the associated label. Values outside `minValue` and `maxValue` are clamped, so the reported value always stays in range.

## Decorative vs labeled icons

The **Icon** component supports two modes:

- **Labeled:** pass a `label` prop to set `role="img"` and `aria-label`, making the icon announced by screen readers
- **Decorative:** omit the `label` prop and the icon receives `aria-hidden="true"`, hiding it from assistive technology

Use labeled icons when the icon conveys meaning on its own. Use decorative icons when accompanying visible text.

## Testing

Accessibility is verified at two levels:

- **Automated tests:** [vitest-axe](https://github.com/chaance/vitest-axe) runs accessibility checks on every component as part of the test suite. These catch common issues like missing labels, invalid ARIA usage, and contrast problems.
- **Live audit in Storybook:** the Storybook a11y addon provides a real-time accessibility panel. Open any component story and check the "Accessibility" tab to see the current audit results.

Automated testing catches many issues, but it cannot catch everything. Manual testing with a keyboard and screen reader is always recommended for thorough coverage.
